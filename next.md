# Fix: rock detector overfitting to mesh-overlay compositing artifact

## Root cause

The annotation mesh is placed ~5cm above the true terrain height so it's
visible to the human annotator and doesn't z-fight/blend with terrain.
When the RGB training frame is generated by baking the overlay directly onto
the camera image, that 5cm offset produces a small dark occlusion sliver
between the mesh and the terrain surface below it, at every single positive
location. This is a deterministic, near-zero-variance visual signature that
correlates 1:1 with "rock present" — much easier for a CNN to key on than
actual rock texture/shape/shading.

Confirmed: model detects only on overlaid frames, not on the same scene's
plain RGB frames → the model learned the compositing artifact, not the
object. This is not a "needs more data" problem, it's a label-leakage
problem — regenerating more data with the same pipeline will reproduce it.

There is a second, independent risk worth checking: because the mesh sits
5cm off the terrain in world space, its projected 2D footprint from an
oblique camera can shift due to parallax. That means existing masks/bboxes
may not just be visually contaminated — they may be spatially offset from
the actual rock silhouette in the RGB frame. Worth a quick check (see
Step 3) independent of the overlay-baking fix.

## Fix

### Step 1 — Stop baking annotations into the training RGB image
Split the current single "overlay and extract" step into two independent
render passes that share the exact same camera transform, intrinsics, and
resolution, but are never composited together:

- **Pass A (training image):** pure camera RGB frame. The annotation
  mesh must not be visible/rendered/blended into this pass at all — not
  even faintly. This is the only image that goes into the training set as
  `image`.
- **Pass B (label source):** the annotation mesh rendered into a separate
  buffer (object-ID / instance-mask / alpha pass) using the same camera.
  Derive segmentation masks and bboxes from this pass only. It never
  touches Pass A's pixels.

Store paired by frame ID (e.g. `rgb_000123.png`, `mask_000123.png`), not as
one flattened composited image. If the current tool only supports "draw
overlay on screen and screenshot," that's the part to replace — it should
render to two targets, not one.

### Step 2 — Fix the mesh placement, not just the compositing
The 5cm offset was presumably a UI/authoring convenience (visibility during
manual boundary drawing), not something the mask pass needs. For mask/bbox
extraction specifically:

- Snap the annotation mesh back onto the terrain surface (raycast each
  vertex down onto the terrain, or a "conform to terrain" op) before
  rendering Pass B, regardless of what offset is used in the interactive
  annotation UI.
- If a nonzero offset is still needed to avoid z-fighting in Pass B's
  render, keep it to sub-mm/epsilon — not 5cm — so it can't shift the
  projected silhouette.

### Step 3 — Sanity-check before regenerating the full dataset
Since a full regenerate+retrain cycle is expensive, validate on a small
batch first (50–100 frames):

- Confirm Pass A is pixel-identical whether or not the annotation mesh
  exists in the scene (toggle mesh visibility off, diff the two renders —
  should be zero difference outside of, well, everywhere, since it should
  never render into Pass A at all).
- Overlay Pass B's mask as a *debug-only* outline on top of Pass A (never
  saved into the training image, just for your eyes) and visually confirm
  the mask hugs the actual rock silhouette with no parallax drift from the
  old 5cm offset.
- Fine-tune briefly on just this small batch and test on genuinely unseen
  plain RGB frames of the same environment. This is the real pass/fail
  signal — if it still only fires on some other artifact, don't scale up
  yet.

### Step 4 — Regenerate full dataset
Once Step 3 passes, regenerate the full dataset through the corrected
two-pass pipeline and retrain.

### Step 5 — Add a standing regression check (so this class of bug can't
silently recur)
- Keep a small held-out set of frames that never pass through the
  annotation/overlay code path at all (independently captured clean RGB +
  independently derived masks). Run inference against this set as a canary
  at the start of every future training run, before committing to a full
  cycle.
- Add an automated assertion in the dataset generation script: RGB output
  must be identical with the annotation mesh toggled on vs. off. If it
  ever isn't, fail the build.

### Step 6 (optional, after root cause is fixed) — harden against residual
artifacts
- Light augmentation (mask boundary erosion/dilation, small scale/shift
  jitter, color jitter) so the model can't re-anchor on some other fixed
  pipeline seam (shadow maps, AA edges, compression differences).
- Include hard-negative frames (terrain only, no rocks) so "absence of
  artifact" isn't itself a usable tell.
